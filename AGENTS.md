## Architecture (Actividad 24 in the spec — do not deviate)

Monolithic 3-layer app: **Node.js + Express** (routes → controllers → middleware), **MySQL** (`mysql2` pool), **EJS** views, **express-session + bcrypt** auth, **multer** for item photos. Structure in `tic-y-stock/`: `routes/`, `controllers/`, `middleware/` (auth, upload, rate-limit, error), `models/` (db.js, user, item, movimiento, alerta, contacto), `views/` (EJS + partials), `public/` (css/js + `vendor/` — libs de F6, vendorizadas — + `uploads/items/` photos, gitignored), `db/schema.sql` (6 tables with FKs) + `db/migracion-*.sql`, `scripts/`, `.env.example`.

Migrations for existing DBs: `& 'C:\xampp\mysql\bin\mysql.exe' -u root --default-character-set=utf8mb4 -e "source db/migracion-01-fks.sql"`, the same for `migracion-02-movimientos.sql` (F5) and `migracion-03-codigos.sql` (F6: agrega `items.codigo_barras` con `UNIQUE` y el backfill `'TIC-' + LPAD(id,6,'0')`). (`source` instead of `<` avoids the shell-redirection quoting mess.) All are idempotent.

  - `test-f5.js` (Node, 134 checks — F5: retiro/devolución, stock, transaction rollback, CHECK/UNIQUE constraints, filters, mis préstamos, "cerrado desde otra pestaña", `items.estado` derivado, borrados bloqueados, cascades) — `node "$env:LOCALAPPDATA\Temp\opencode\test-f5.js"`

  - `revisa-html-f6.js` (el mismo chequeo estructural, aplicado a las vistas de F6: escaneo, elección, formularios con contexto y etiquetas) — `node "$env:LOCALAPPDATA\Temp\opencode\revisa-html-f6.js"`
  - `resiliencia-f5.js` (stops MySQL, hits 11 routes, expects 503s + a live process, then restarts MySQL) — `node "$env:LOCALAPPDATA\Temp\opencode\resiliencia-f5.js" apagar`. XAMPP's mysqld is started as `--defaults-file=C:\xampp\mysql\bin\my.ini --standalone` from `C:\xampp\mysql` (there is **no** `C:\xampp\mysql\my.ini`).
  - **Prefer writing new checks in Node** (`fetch` + `URLSearchParams` + a `FormData`); all of these live outside the repo because they hardcode this machine's MySQL path.
- Windows gotcha: PowerShell blocks `npm`/`npx` `.ps1` shims → use `npm.cmd` / `npx.cmd` (and `cmd /c` for `mysql < file` redirection). ALSO: don't name a PowerShell function `H` (collides with the `Get-History` alias).
- **curl.exe in PowerShell**: pass extra args as an ARRAY (`@('-X','POST','-d',...)`), never as one string — PowerShell splits it on spaces and the `&` of query strings breaks the request. Always use `-X POST`, never a bare `POST` arg (curl reads it as an extra URL and returns `000`). Even then it is fragile: just write the test in Node.
- **Never edit UTF-8 source files with `Get-Content`/`Set-Content` round-trips** — PowerShell 5.1 reads/writes with the system codepage and mangles accented characters (and `Get-Content -Raw` + regex then fails to match accented patterns, silently). Use the edit tool.
- `node -e "..."` from PowerShell mangles quotes. Write a temp `.js` file and run it.
- `mysql2` `pool.query()` resolves to `[rows, fields]`. `const [rows] = ...` gets the rows; `const [, x] = ...` gets the **field metadata**, not data (a bug that made a test silently do `DELETE ... WHERE id = undefined`). The mirror-image trap: `const [carrera] = await pool.query('SELECT * ...')` binds the **array of rows**, so `carrera.id` is `undefined` while `carrera[0].id` works — and nothing throws, the test just asserts against `undefined`.

## Gotchas

- **No accented identifiers.** Windows MySQL client mangles UTF-8 accents (table/column names AND form field names must be ASCII: `contrasena_hasheada`, `confirmar_contrasena`, `SEED_CONTRASENA`). Spanish is fine in UI text and error messages, not in identifiers/fields or env var names.
- `.env` supported (`PORT`, `DB_*`, `SESSION_SECRET`, `SEED_*`); defaults target XAMPP MySQL (root, no password) and `0.0.0.0:3000` (school LAN access).
- Session: cookie `ticstock.sid`, httpOnly, 30 min inactivity expiry (rolling) — requirement T-12.
- **`requireAuth` is async and re-reads the user from the DB on every authenticated request.** Don't "optimize" it back to trusting `req.session.user`: that is what let a demoted/banned/deleted account keep admin access for up to 30 minutes. `requireSuperusuario` is therefore sync (it reads the already-refreshed role). An async middleware here MUST catch its own errors — Express 4 does not catch promise rejections from middleware.
- **Never name a helper the same as a route handler in the same file.** `crearSesion` vs handler `iniciarSesion`: when both were named `iniciarSesion`, hoisting made the handler shadow the helper and login recursed into itself forever (every request hung, no error logged).
- `regenerate()` on login is what prevents session fixation; `destroy()` on logout. A `const [, x] = await pool.query()` picks up **field metadata**, not rows.
- Roles: `usuario` (alumno, via public register, → `/panel`) and `superusuario` (docente/Jefe de Taller, **only** via `db:seed`, → `/admin`). `/panel` = catalog + filters + detail; `/admin` = dashboard, CRUD inventario, gestión de usuarios (guards: can't delete own account nor demote/delete the last `superusuario`).
- `/institucional` and `/contacto` are public (no auth). POST `/contacto` stores a `contactos` row. `admin` router uses `router.use(requireAuth, requireSuperusuario)` scoped by mounting at `/admin` — do NOT add un-scoped `router.use` that would shadow public routes.
- Item photos: `multer` → `public/uploads/items/` (5 MB, gitignored). The filter requires **MIME in the allowlist AND extension in the allowlist**, and the stored extension comes from the MIME — storing the original extension let a `.html` typed as `image/png` be served back as HTML (stored XSS). Keep `X-Content-Type-Options: nosniff` in `server.js`.
- The hidden field preserving the photo on edit is `foto_actual`, NOT `foto`: two inputs sharing a `name` would make `req.body.foto` an array and `String(array)` would store `"/uploads/a.png,b.png"` in the DB.
- **Stock crítico means `cantidad < cantidad_minima`, not `<=`.** With `<=`, every single-unit item (an oscilloscope at 1/1) is permanently red. Used in `Item.stockCritico()`, `buildFiltros({stockCritico})` and the `text-critical` class in `inventario.ejs` — keep all three in sync.
- **Lengths must be validated against the `VARCHAR` widths.** XAMPP's MySQL runs without `STRICT_TRANS_TABLES`, so over-long values are silently truncated (200 chars stored as 120). `maxlength` on the input + a check in the controller, with the constants at the top of each controller.
- `/admin/inventario` paginates at 25/page with server-side filters (q, categoria, estado, ubicacion, stock_critico, orden). `orden` goes through a whitelist map; the filter form carries a hidden `pagina=1` so filtering jumps back to page 1. The live search submits that form (debounced) instead of re-rendering rows in JS — one source of truth, and the URL is shareable.
- `/logout` is POST-only (a GET can be triggered from any site with `<img src="/logout">`); the navbar wraps the button in `form.topbar-logout`.
- Render errors **only** via `renderError(req, res, codigo, detalle, titulo)` from `middleware/error.middleware.js`. It always supplies `user` and `seccion` (nav needs both; a missing `seccion` is a `ReferenceError` inside EJS) and uses `detalle`, not `mensaje`, so it does not clobber the flash message the navbar renders from `mensaje`.
- **Wrap every async route handler in `asyncHandler()`** (`middleware/error.middleware.js`). Express 4 does not catch promise rejections: unwrapped, a MySQL failure becomes an `unhandledRejection` that **kills the server process** (verified: it died on the first `POST /login` with MySQL down). Wrapped, it returns a 503 page and the server survives 20+ consecutive DB failures. `errorHandler` must stay last in `server.js`.
- `errorHandler` maps `ER_ROW_IS_REFERENCED_2` to 409 (a `solicitudes` FK blocks deleting the user/item) instead of a generic 500.
- FK policy: CASCADE from `items`/`usuarios` to `movimientos` to `alertas`; **RESTRICT** on `solicitudes.id_usuario` / `solicitudes.id_item` (an administrative record must be resolved by hand).
- `server.js` pings MySQL at boot and warns with the recovery steps if it can't connect; `pool.on('error')` logs dropped idle connections instead of crashing.
- **No new npm dependencies** if it can be avoided: RNF-04 requires the app to run on the school network without external internet, so `npm install` on a school machine must stay unnecessary.
- The Figma export (React/Vite/Tailwind) in `Figma/` uses `figma:asset/` imports and a `figmaAssetResolver` in its vite config — irrelevant to `tic-y-stock`; don't port those.

### Movimientos (F5) — decisiones que hay que respetar

- **Una devolución es una fila propia que apunta al retiro que cierra** (`movimientos.id_retiro`, FK a `movimientos.id`, `ON DELETE CASCADE`), no una columna tipo `devuelto_en`. Así el historial es un log de eventos auditable, "mis préstamos activos" es un anti-join, y una alerta puede colgar del préstamo en F7. `UNIQUE(id_retiro)` garantiza que un retiro se devuelva una sola vez; un `CHECK` ata `tipo` con `id_retiro`. Las devoluciones **parciales** están fuera de alcance: la devolución repone la cantidad completa del retiro.
- **`ABIERTO` (en `models/movimiento.model.js`) es la única definición de "préstamo activo"**: `m.tipo = 'retiro' AND NOT EXISTS (SELECT 1 FROM movimientos d WHERE d.id_retiro = m.id)`. Se usa en el `SELECT_BASE` (alias `abierto`), en `buildFiltros({soloAbiertos})`, en `retirosAbiertos()`, `prestamosActivosDe()`, `activosPorItem()`, `contarPrestamosActivos()`, `contarPrestamosAbiertosDe()` y en el `CASE` de `recalcularEstado()`. Si tocás uno, tocás el string; no lo reescribas inline en ningún otro lugar.
- **`items.estado` se DERIVA de los movimientos** (decisión del usuario, 2026-10-05), pero solo en un eje: `baja` y `en_reparacion` son del docente y ningún movimiento ni guardado los pisa; `disponible` / `prestado` los calcula la app. La precedencia entera vive en el `CASE` de `Movimiento.recalcularEstado(idItem, conn)` (`models/movimiento.model.js`), que se llama desde `registrarRetiro`, `registrarDevolucion`, `Item.create`, `Item.update` y… ya no desde `User.remove`, porque el borrado se niega si hay préstamos abiertos. Si tocás el `CASE`, tocás el `migracion-02-movimientos.sql` (backfill) y el aviso de `mensajeGuardado` en `item.controller.js`, que son los otros dos lugares donde la regla se refleja.
- **`recalcularEstado` vive en `movimiento.model.js`, no en `item.model.js`**, para que el predicado de préstamo activo siga teniendo una sola definición (`ABIERTO`). `item.model.js` y `user.model.js` lo requieren en un solo sentido; si alguna vez lo movés, mantenelo de un solo lado o se forma un ciclo de `require` con exports parciales.
- **`Item.remove` y `User.remove` devuelven `{ ok, error }`, no un boolean**, y se niegan si hay préstamos abiertos (`Movimiento.contarPrestamosAbiertosDe`). No es burocracia: los FK son CASCADE, así que borrar en cascada se lleva el asiento que dice que el material está afuera y el stock queda corto sin que nadie haya tocado el inventario. Los dos controladores tienen que mirar `borrado.ok`. Los tests de cascada de `test-f5.js` usan SQL crudo a propósito, para verificar que la cascada de la base sigue funcionando aunque la app la frene.
- La columna **Préstamos** del inventario (`Movimiento.activosPorItem(idsDeLaPagina)` — una sola consulta para toda la página, nunca una por fila) es ahora el control visible de que el estado coincide con los movimientos.
- **Retiro y devolución escriben en dos tablas, así que van en transacción**: `db.withTransaction(fn)` (`models/db.js`) saca una conexión del pool, hace commit/rollback y la libera siempre. Adentro del callback **todo va por `conn`**, nunca por `pool.query` (eso sería otra conexión, fuera de la transacción). El retiro usa `SELECT ... FOR UPDATE` sobre el ítem: es lo que garantiza que `items.cantidad` no pueda quedar negativa con dos retiros simultáneos.
- **Los errores de validación de negocio NO son excepciones.** `registrarRetiro` / `registrarDevolucion` devuelven `{ ok: true, id, ... }` o `{ ok: false, errores: { campo: mensaje } }` y el controlador los pinta en el formulario. "No hay stock", "ya fue devuelto", "está dado de baja" son el camino normal de un formulario mal completado.
- **El alumno es de solo lectura en F5.** Registra el retiro y la devolución el `superusuario`, para cualquiera. El flujo de pedido/aprobación es F8 (`solicitudes`). `/panel/mis-prestamos` sirve para todos los autenticados.
- **Ojo con los tests del historial**: la barra de filtros de `/admin/movimientos` tiene un `<select>` con TODOS los ítems y TODOS los usuarios, así que el nombre del ítem aparece en el HTML aunque la tabla esté filtrada. Para preguntar "¿está en los resultados?" hay que mirar el `<tbody>` (helper `filas()` en `test-f5.js`).
- **Las ramas de "vacío" de los formularios tienen que mostrar el error, no taparlo.** Si el préstamo se devolvió desde otra pestaña entre la carga del form y el envío, el `<select>` queda vacío y el mensaje "ya fue devuelto" se perdía: el usuario veía "no hay préstamos abiertos" sin entender por qué su acción falló. `movimiento-devolucion.ejs` y `movimiento-retiro.ejs` pasan `errores.id_retiro` / `errores.id_item` al empty state.
- **Las listas de los formularios se releen DESPUÉS del intento, no antes.** `crearRetiro`/`crearDevolucion` llaman a `datosFormularioRetiro()`/`datosFormularioDevolucion()` recién cuando van a renderizar. Si se leen antes (que es lo más natural), el `<select>` ofrece el ítem sin stock o el préstamo ya cerrado, y el docente entra en un loop: elige la única opción que ve, falla, vuelve a ver exactamente la misma opción. Es el mismo criterio del punto anterior, aplicado al caso en que la lista no queda vacía.
- **La lista de usuarios tiene que salir en el mismo orden en el GET y en el re-render del error**, o el `<option selected>` se mueve de lugar y el docente ve cambiar la persona que estaba por registrar: de ahí `usuariosOrdenados()` en vez de `User.findAll()` con un `.sort()` copiado en cada render.
- **`paginacion`, `paginacion-info` e `is-disabled` no tenían regla en `styles.css`** (existían en `inventario.ejs` desde el sprint anterior y se veían sin estilo). Agregadas junto con `badge--mov`, `badge--activo`, `mov-nota`, `field-hint` y `field--check`. `revisa-html-f5.js` existe para que no vuelva a pasar: cruza cada `class=` del HTML contra la hoja de estilos.

### Escaneo y etiquetas (F6) — decisiones que hay que respetar

- **El código de barras es del sistema, no del docente.** `items.codigo_barras` se deriva del `id` (`'TIC-' + LPAD(id,6,'0')`, ej. `TIC-000073`), con `UNIQUE`, y lo calcula `Item.create` a partir del `insertId`. La UI lo muestra **de solo lectura**: el docente no lo inventa ni lo pisa al editar. `Item.findByCodigo` busca con `UPPER(TRIM(...))` para tolerar lo que manda un lector USB (mayúsculas, espacios).
- **El escaneo se resuelve en el servidor.** `GET /admin/movimientos/escanear?codigo=...` redirige al form de retiro si hay stock, al de devolución si hay algo prestado, y **no adivina** cuando las dos cosas son posibles: en ese caso renderiza `movimiento-escanear.ejs` con la pantalla de elección. Un ítem `baja` o sin stock ni préstamos se explica en pantalla (`aviso`), no con un error suelto. La decisión vive en `movimiento.controller.js` (`escanear` / `decidirDestino`).
- **La API `GET /api/items/:codigo` es sólo la confirmación en vivo** (cámara/USB): devuelve campos no sensibles y **pide sesión** (`requireAuth`, aunque alcance con ser alumno). Si la sesión venció devuelve 302 al login y `escaner.js` cae al tipeo manual. El submit real del movimiento sigue yendo por el formulario, nunca por la API.
- **El lector USB no necesita librería**: se comporta como un teclado y manda Enter, así que dispara el submit del `<form>` (camino 1). La cámara (camino 2, contingencia) usa **ZXing vendorizado**; el tipeo manual (camino 3) es el mismo formulario que el USB. La página **funciona sin JS**: la resolución también existe server-side.
- **Libs vendorizadas, sin CDN** (RNF-04: la red del colegio no tiene salida a internet). `public/vendor/zxing-0.23.0.min.js` (Apache-2.0) y `public/vendor/jsbarcode-3.12.3.min.js` (MIT); procedencia y licencias en `public/vendor/README.md`. **No** se agregó una dependencia npm para esto.
- **Las etiquetas se derivan del id** y se dibujan con JsBarcode en `[data-codigo]` (formato `CODE128`), con el código legible debajo como respaldo (sirve aunque el dibujo no cargue). Dos vistas: reimpresión individual (`/admin/inventario/:id/etiqueta`) y hoja completa (`/admin/inventario/etiquetas`, agrupada por categoría y filtrable). El print CSS esconde navbar y controles.
- **`movimientos.codigo_escaneado` es el rastro físico**: guarda la etiqueta que se leyó (o `NULL` si fue tipeo manual sin escaneo). Retiro y devolución llevan el código en un campo oculto; la devolución además filtra la lista de préstamos abiertos por el `id_item` escaneado.
- **Rutas literales antes de `:id`** en `routes/admin.routes.js`: `/inventario/etiquetas` va antes de `/inventario/:id/etiqueta` (y `/inventario/nuevo` antes de `:id`), si no "etiquetas"/"nuevo" se comen como `:id`.
- `revisa-html-f6.js` cruza cada `class=` de las vistas F6 contra `styles.css` — así se detectó que `.escaner-form` no tenía regla (el mismo tipo de olvido que `paginacion` en F5).
